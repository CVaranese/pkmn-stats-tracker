## 2. Team sheets per Pokémon

Today: one paste per player per game (`site/<league>/mock/<game>-<player>.txt`, listed in `index.json` `sheets`).
`TS.attachSheets` gives a side its sets only when **all 6** team-preview Pokémon pair with the sheet. In memory the
sets are already per Pokémon: `addToPool` keeps each player's sets one by one for guessing max HP in other games.

What goes wrong with all-or-nothing:
- Zolo's Week 1 paste had Vaporeon where the game had Scrafty: none of its 5 correct sets applied until the file was
  edited by hand, which also overwrote the paste as the player gave it.
- A set pieced together from the game (Suicune, Scrafty) has to live inside someone's paste file.

Proposal:
- Keep the paste files as they are: they are what players hand over, and adding one stays a copy-paste.
- Match per Pokémon for library games: the game and player are already known from `index.json`, so the 6-of-6 rule
  only matters for a sheet pasted into Main viewer's box (where it picks the side). Each Pokémon gets its own set
  from that game's paste if it has one; the rest fall back as today (the player's other sheets, Smogon, base stats).
- Hand-made sets in their own place, e.g. `index.json` `set_fixes: {player: {Pokémon: "set text"}}` or a
  `mock/<game>-<player>.fix.txt` read after the paste, so the paste stays untouched.
- Each Pokémon says where its set came from (paste / other game / pieced from the game / guess), shown where the
  ~ mark is now.

## 3. Data size on GitHub Pages

GitHub's limits (docs.github.com, Pages limits, read 2026-10-29): published site at most 1 GB; repository
recommended under 1 GB; 100 GB a month of traffic (soft); deploys time out after 10 minutes; the 10-builds-an-hour
limit doesn't apply to an Actions workflow (ours).

Measured (tested, 2026-10-29):

| What | Size |
|---|---|
| `site/` (one copy) | 26 MB, of which sprites 21.6 MB (213 animated GIFs, 97 KB each on average; 222 pixel PNGs, 4 KB) |
| Deployed (live + `next/` preview) | about 52 MB, 5% of the 1 GB limit |
| Saved games | Pinecord 51 games 528 KB; Super Champions 168 games 1.5 MB; about 10 KB a game |
| `site/data/` | 1.6 MB (learnsets 1.1 MB, loaded only for a hidden-Zoroark check) |
| Git history (packed) | 15.5 MB |

Verdict: no problem, now or for several more seasons. A season of 100 games adds about 1 MB.

What a visit costs (estimate): a Main viewer game with 12 animated sprites is about 1.2 MB; opening Players or
Pokémon loads every saved game (0.5 MB Pinecord, 1.5 MB Super Champions) plus every team sheet, and recounts them
in the browser. At 2-4 MB a full visit, 100 GB is 25,000-50,000 visits a month.

Worth watching, not fixing yet:
- Request count: Super Champions' Players tab makes about 170 requests. If leagues grow to several hundred games,
  one combined file per league (made by a tool, like `build_pages.py`) or stats counted ahead of time would cut it.
- Each log is parsed twice when it has a Zoroark check (`prepareIllusion`, then `gameRows`), old finding #13.
- Animated sprites are 96% of the site. Fine at 52 MB; if it ever matters, WebP or only the brought Pokémon animated.

## 4. Tests

What runs: `tests/index.html` (270 checks from 158 `check(...)` calls, many over tables; 10 hand-counted real
replays plus synthetic logs) and `tests/test_tools.py` (11 tests). Both pass. Neither runs on GitHub: a push to
`main` deploys whatever is there.

Covered well: kill / death / damage credit, hazards, healing, switches, Illusion and hidden Zoroark, luck counts and
scoring, key moments, MVP, survival, Mega / Z, status, momentum, fetch errors, CSV / TSV escaping, team sheet
parsing and max HP, sets (`League.sets`), the KO matrix pairs, fantasy points, link parsing, page freshness, releases.

Each check was looked at for whether it can fail: none asserts a constant or only "something came back". Each real
fixture has hand-counted numbers. I didn't judge every one of the 270 for overlap; the sections each test a
different rule, so I found nothing to delete in `tests/`.
